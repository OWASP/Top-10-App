## LLM01 — Prompt Injection

- Risk ID: `llm-2026-LLM01`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Untrusted input such as user text, retrieved content, tool output, an image, or memory changes the model's behavior, because an LLM does not separate instructions from data.

### Real-world example

A web page summarized by an assistant contains hidden text that tells the model to send the conversation to an attacker-controlled URL.

### Test for it

Red-team with indirect injections in documents, emails, images and tool output, and test against adaptive attackers who know your defenses.

### How to fix it

Assume injection will succeed: keep least privilege, hold credentials outside the model, mediate privileged actions deterministically, and require human approval for irreversible steps.

### Code samples

#### Vulnerable (python)

````python
prompt = system_prompt + web_page + user_question
result = model.generate(prompt)
execute(result)
````

#### Secure (python)

````python
untrusted = strip_invisible_characters(web_page)
prompt = system_prompt + label_as_data(untrusted) + user_question
result = model.generate(prompt)
action = validate_schema(result)
require_approval_for_privileged(action)
````

### Quiz

#### llm-2026-q01 (easy)

Which of these can carry a prompt injection into an LLM application?

1. Only what the user types in the chat box
2. Retrieved documents, tool output, images and persistent memory **(correct)**
3. Only the system prompt

Explanation: An LLM treats all of these as tokens in one stream. Indirect injection hides instructions in content the user never typed, including multimodal input and memory.

## LLM02 — Sensitive Information Disclosure

- Risk ID: `llm-2026-LLM02`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

The system exposes confidential, regulated or proprietary data through answers, reasoning traces, tool arguments, retrieved chunks, embeddings, logs or side channels.

### Real-world example

Extended-thinking traces logged to a shared APM project expose retrieved medical data while the final answer is redacted.

### Test for it

Probe for other users' data, system prompts and secrets, and inspect traces, logs, embeddings and timing, not just the final answer.

### How to fix it

Authorize before retrieval, minimize context, redact outputs and traces, and treat embeddings, logs and side channels as sensitive data.

### Code samples

#### Vulnerable (python)

````python
prompt = build_prompt(retrieve(question), question)
answer = model.generate(prompt)
logger.info(answer)  # full trace to a shared APM project
````

#### Secure (python)

````python
chunks = authorized_chunks(question, user)  # ACL enforced in the index query
answer = model.generate(build_prompt(chunks, question))
logger.info(redact(answer, policy=DLP_POLICY))
````

## LLM03 — Excessive Agency

- Risk ID: `llm-2026-LLM03`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

An LLM can take damaging actions because it has too much functionality, too many permissions, or too much autonomy.

### Real-world example

A mail assistant with send and delete functions is tricked by an injected email into forwarding the inbox to an attacker.

### Test for it

Ask what the agent can do if it is fully compromised: which tools, scopes and irreversible actions can it reach?

### How to fix it

Minimize tools and permissions, avoid open-ended tools, execute in the user's context, mediate every call, and require approval for high-impact actions.

### Code samples

#### Vulnerable (python)

````python
tools = [read_email, send_email, delete_email]
agent.run(task, tools=tools, identity=service_account)
````

#### Secure (python)

````python
tools = [read_email]  # least functionality
agent.run(task, tools=tools, identity=user_oauth_token(read_only=True))
# Sending and deleting are separate, human-approved actions.
````

### Quiz

#### llm-2026-q02 (easy)

A mail assistant can read, send and delete messages, and runs as a service account with access to every mailbox. Which risk does this describe?

1. Prompt injection
2. Excessive agency **(correct)**
3. Misinformation

Explanation: The problem is excessive functionality, permissions and autonomy. Injection may trigger abuse, but the damage comes from granting the agent more capability than the task needs.

## LLM04 — Supply Chain

- Risk ID: `llm-2026-LLM04`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Training data, models, adapters, conversion pipelines or serving software are outdated, tampered with, or resolved by a mutable reference.

### Real-world example

An attacker re-registers a released model namespace on a public hub, and pipelines that pull by name alone fetch the attacker's weights.

### Test for it

Trace every model, adapter, dataset and serving dependency to an immutable digest and a verified signer.

### How to fix it

Vet suppliers, pin and verify artifacts, keep an AI BOM, scan and patch, and treat conversion and merge services as high-risk release gates.

### Code samples

#### Vulnerable (shell)

````shell
pip install random-llm-wrapper
huggingface-cli download acme/assistant --revision main
````

#### Secure (shell)

````shell
pip install random-llm-wrapper==1.2.3  # hash-pinned
huggingface-cli download acme/assistant --revision <commit-sha>
# Verify the signed manifest and record the digest in the AI BOM.
````

## LLM05 — Data and Model Poisoning

- Risk ID: `llm-2026-LLM05`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Manipulated training, fine-tuning, embedding or feedback data embeds backdoors, bias or unsafe behavior that survives normal evaluation.

### Real-world example

A handful of poisoned documents in a RAG corpus steer answers for a targeted query while looking ordinary to reviewers.

### Test for it

Probe with trigger phrases and canary queries, and monitor data lineage, retrieval outliers and behavior drift.

### How to fix it

Track lineage and versions, validate and isolate data by trust tier, red-team triggers, and keep the ability to roll back and retrain.

### Code samples

#### Vulnerable (python)

````python
for doc in scrape_public_sources():
    vector_store.add(embed(doc))
````

#### Secure (python)

````python
for doc in scrape_public_sources():
    if not passes_provenance_and_quality_checks(doc):
        continue
    vector_store.add(embed(doc), metadata={'source': doc.url, 'trust': 'external'})
````

## LLM06 — Unbounded Consumption

- Risk ID: `llm-2026-LLM06`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Uncontrolled inference and tool use let attackers exhaust service availability, budget or model intellectual property.

### Real-world example

A long agent session grows its context every turn, turning a cent of compute into hundreds of dollars without tripping request-rate limits.

### Test for it

Send oversized inputs, reasoning-loop prompts and multi-turn tool fan-out, and check token and cost ceilings rather than only requests per second.

### How to fix it

Use token and cost budgets, hard spend caps, size and step limits, circuit breakers, and per-tenant monitoring.

### Code samples

#### Vulnerable (javascript)

````javascript
app.post('/chat', async (req, res) => {
  res.json(await model.generate(req.body.prompt));
});
````

#### Secure (javascript)

````javascript
app.post('/chat', async (req, res) => {
  await enforceBudget(req.user, estimateTokens(req.body.prompt));
  res.json(await model.generate(req.body.prompt, { maxTokens: 512 }));
});
````

- [OWASP Top 10 for LLM Applications 2026 — LLM06:2026 Unbounded Consumption (pp. 38–42)](https://genai.owasp.org/llm-top-10/)

## LLM07 — Misinformation

- Risk ID: `llm-2026-LLM07`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Fluent but incorrect, incomplete or unsupported output is trusted and drives a human decision or an automated action.

### Real-world example

A support agent misreads a policy and issues a refund that the terms do not allow.

### Test for it

Feed stale, contradictory and adversarially seeded sources, and check whether the system verifies claims before acting.

### How to fix it

Ground claims in authoritative sources, separate generation from action, validate state and tool arguments, and keep a deterministic or human check on high-impact steps.

### Code samples

#### Vulnerable (python)

````python
if model.answer('Is this refund allowed?') == 'yes':
    issue_refund(order)
````

#### Secure (python)

````python
claim = model.answer('Is this refund allowed?')
if verify_refund_policy(order) and claim_is_grounded(claim, POLICY_DOCS):
    issue_refund(order)
else:
    escalate(order)
````

## LLM08 — Hidden Context Exposure

- Risk ID: `llm-2026-LLM08`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

System prompts, tool schemas, policy logic or secrets placed in hidden context are extracted, inferred or reconstructed.

### Real-world example

Conversational probing reveals the tool list and permission rules, giving an attacker targets for later prompt injection.

### Test for it

Try to extract instructions, tool schemas and refusal rules, then ask what an attacker gains from knowing them.

### How to fix it

Put no secrets in context, enforce authorization outside the model, and design as if all hidden context is public.

### Code samples

#### Vulnerable (python)

````python
system_prompt = f'''
You are a support agent.
DB_PASSWORD={db_password}
Only admins may issue refunds.
'''
````

#### Secure (python)

````python
system_prompt = 'You are a support agent. Use the provided tools.'
# Authorization and refund limits are enforced by the refund service,
# not by instructions the model can leak or ignore.
````

### Quiz

#### llm-2026-q03 (easy)

Where should authorization rules for an LLM application live?

1. In the system prompt
2. In deterministic application code outside the model **(correct)**
3. In the model's refusal training

Explanation: Hidden context can leak and instructions can be overridden. Authorization must be enforced by code and by downstream services, not by the model.

## LLM09 — Vector and Embedding Weaknesses

- Risk ID: `llm-2026-LLM09`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Similarity search over embeddings enables cross-tenant leakage, inversion, retrieval poisoning, jamming and semantic-cache attacks.

### Real-world example

A shared vector index filters by tenant after similarity search, so timing and result counts reveal another tenant's documents.

### Test for it

Probe with cross-tenant queries, raw scores and near-duplicate documents, and treat an embeddings-only backup as a document leak.

### How to fix it

Enforce tenant scope inside the index query, segment trust tiers, track provenance, and validate content before embedding.

### Code samples

#### Vulnerable (python)

````python
results = index.search(query_vector, top_k=10)
return [r for r in results if r.tenant_id == user.tenant_id]
````

#### Secure (python)

````python
results = index.search(
    query_vector, top_k=10, filter={'tenant_id': user.tenant_id}
)
# The filter is applied inside the index, not after retrieval.
return results
````

### Quiz

#### llm-2026-q04 (medium)

A shared vector index filters results by tenant after similarity search has run. What is the risk?

1. Cross-tenant leakage through results, scores, timing or counts **(correct)**
2. Nothing, as long as every document has a tenant tag
3. Only a small performance cost

Explanation: Similarity search across the full index can reveal the existence and topic of another tenant's documents even when the results are filtered afterwards. Scope the query inside the index.

- [OWASP Top 10 for LLM Applications 2026 — LLM09:2026 Vector and Embedding Weaknesses (pp. 50–54)](https://genai.owasp.org/llm-top-10/)

## LLM10 — Improper Output Handling

- Risk ID: `llm-2026-LLM10`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Model output reaches shells, SQL, browsers, file paths or other sinks without validation or context-aware encoding.

### Real-world example

A coding assistant's answer is auto-executed, and injected text turns it into a destructive shell command.

### Test for it

Treat model output as user input: try XSS, SQL injection, path traversal and ANSI escapes at every sink.

### How to fix it

Validate against a strict schema, encode for the destination context, parameterize queries, and neutralize control characters before logs, terminals or IDEs.

### Code samples

#### Vulnerable (javascript)

````javascript
const sql = await llm.generate(`Write a query for ${input}`);
db.query(sql);
````

#### Secure (javascript)

````javascript
const plan = QueryPlan.parse(await llm.generate(`Write a query for ${input}`));
db.query(plan.sql, plan.params);  // validated schema + parameterized
````

### Quiz

#### llm-2026-q05 (medium)

LLM output will be used to build a database query. What is the correct handling?

1. Ask the model to escape quotes and trust the result
2. Validate a structured query plan and use parameterized statements **(correct)**
3. Trust the output if the model temperature is zero

Explanation: Model output is untrusted input. Validate it against a strict schema and keep data out of the SQL syntax with parameters; deterministic settings do not make output safe.

### References

- [OWASP Top 10 for LLM Applications 2026 — LLM10:2026 Improper Output Handling (pp. 55–57)](https://genai.owasp.org/llm-top-10/)

- Probe for system prompt and tool schema leakage
- Test tenant isolation in RAG and vector search
- Check token, spend and agent step limits

### Agent safety rules

- ID: `llm-2026-cheat-02` · last reviewed: 2026-10-21

- Grant the fewest tools and permissions that work
- Run tools in the user's context, not a service account
- Require human approval for irreversible actions
- Treat memory writes as privileged operations
- Bound every run with step, time and cost limits
