## API1 — Broken Object Level Authorization

- Risk ID: `api-2023-API01`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

APIs expose object IDs without checking that the caller owns the object.

### Real-world example

GET /api/orders/42 returns another customer's order when the caller changes the ID.

### Test for it

Swap object IDs between two accounts on every endpoint.

### How to fix it

Check ownership on every object access. Use unguessable IDs as a second layer.

### Code samples

#### Vulnerable (javascript)

````javascript
app.get('/api/orders/:id', async (req, res) => {
  const order = await Order.findByPk(req.params.id);
  res.json(order);
});
````

#### Secure (javascript)

````javascript
app.get('/api/orders/:id', async (req, res) => {
  const order = await Order.findByPk(req.params.id);
  if (!order) return res.sendStatus(404);
  if (order.userId !== req.user.id) return res.sendStatus(403);
  res.json(order);
});
````

### Quiz

#### api-2023-q01 (easy)

Changing /api/orders/42 to /api/orders/43 returns another customer's order. Which risk is this?

1. Broken Object Level Authorization **(correct)**
2. Broken Authentication
3. Unsafe Consumption of APIs

Explanation: The endpoint accepts an object ID without checking that the caller owns that object. That is broken object level authorization.

## API2 — Broken Authentication

- Risk ID: `api-2023-API02`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Weak tokens, missing rate limits or flawed login flows undermine authentication.

### Real-world example

An API accepts a JWT with no signature and lets the caller choose the subject.

### Test for it

Try credential stuffing, unsigned JWTs and password reset abuse.

### How to fix it

Use standard auth, short-lived tokens, MFA and strict rate limits.

### Code samples

#### Vulnerable (python)

````python
payload = jwt.decode(token, options={'verify_signature': False})
````

#### Secure (python)

````python
payload = jwt.decode(token, SECRET_KEY, algorithms=['HS256'])
````

## API3 — Broken Object Property Level Authorization

- Risk ID: `api-2023-API03`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Users read or write object properties they should not see or change.

### Real-world example

A profile update accepts {"role": "admin"} and mass-assigns it.

### Test for it

Add fields like role or isAdmin to update requests. Compare responses across roles.

### How to fix it

Return only needed fields. Block mass assignment with allow-lists.

### Code samples

#### Vulnerable (javascript)

````javascript
const user = await User.findByPk(req.params.id);
await user.update(req.body);
````

#### Secure (javascript)

````javascript
const { name, email } = req.body;
await user.update({ name, email });
````

### Quiz

#### api-2023-q04 (medium)

Which change prevents mass assignment on a profile update?

1. Binding only an allow-listed set of fields **(correct)**
2. Returning 404 for unknown fields
3. Logging the whole request body

Explanation: Copy only the fields a user may change, so extra properties such as role or isAdmin in the request body are ignored.

### References

- [OWASP API Security Top 10 2023 — API3 Broken Object Property Level Authorization](https://api-security.owasp.org/editions/2023/en/0xa3-broken-object-property-level-authorization/)

## API4 — Unrestricted Resource Consumption

- Risk ID: `api-2023-API04`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

There are no limits on requests, payload size or costly operations.

### Real-world example

A search endpoint accepts limit=1000000 and returns the whole table.

### Test for it

Send large payloads, deep queries and bursts of requests.

### How to fix it

Set rate limits, size limits, timeouts and spend caps.

### Code samples

#### Vulnerable (python)

````python
limit = int(request.args['limit'])
return db.query(limit=limit)
````

#### Secure (python)

````python
limit = min(int(request.args.get('limit', 20)), 100)
# Also apply rate limits, timeouts and query cost caps.
return db.query(limit=limit)
````

### References

- [OWASP API Security Top 10 2023 — API4 Unrestricted Resource Consumption](https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption/)

## API5 — Broken Function Level Authorization

- Risk ID: `api-2023-API05`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Regular users can call administrative or privileged functions.

### Real-world example

A normal user calls DELETE /api/admin/users/42 and succeeds.

### Test for it

Call admin endpoints and change HTTP methods as a normal user.

### How to fix it

Deny by default. Check roles on every function, not just in the UI.

### Code samples

#### Vulnerable (javascript)

````javascript
app.delete('/api/admin/users/:id', async (req, res) => {
  await User.destroy({ where: { id: req.params.id } });
  res.sendStatus(204);
});
````

#### Secure (javascript)

````javascript
app.delete('/api/admin/users/:id', requireRole('admin'), async (req, res) => {
  await User.destroy({ where: { id: req.params.id } });
  res.sendStatus(204);
});
````

### Quiz

#### api-2023-q02 (easy)

A normal user calls DELETE /api/admin/users/42 and succeeds. Which control is missing?

1. Object-level authorization
2. Function-level authorization **(correct)**
3. Rate limiting

Explanation: The request reaches an administrative function that the caller's role should not permit. Hiding the button in the UI is not an authorization control.

### References

- [OWASP API Security Top 10 2023 — API5 Broken Function Level Authorization](https://api-security.owasp.org/editions/2023/en/0xa5-broken-function-level-authorization/)

## API6 — Unrestricted Access to Sensitive Business Flows

- Risk ID: `api-2023-API06`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Sensitive flows such as purchases or sign-ups can be abused at scale.

### Real-world example

A script buys all limited stock in seconds through the checkout API.

### Test for it

Script the flow at speed. Does anything slow or block it?

### How to fix it

Add bot detection, per-user limits and step-up checks on key flows.

### Code samples

#### Vulnerable (javascript)

````javascript
app.post('/checkout', async (req, res) => {
  res.json(await placeOrder(req.user.id, req.body.items));
});
````

#### Secure (javascript)

````javascript
app.post('/checkout', botCheck, perUserLimit('checkout', 5), async (req, res) => {
  res.json(await placeOrder(req.user.id, req.body.items));
});
````

### References

- [OWASP API Security Top 10 2023 — API6 Unrestricted Access to Sensitive Business Flows](https://api-security.owasp.org/editions/2023/en/0xa6-unrestricted-access-to-sensitive-business-flows/)

## API7 — Server Side Request Forgery

- Risk ID: `api-2023-API07`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

The API fetches a URL supplied by the user.

### Real-world example

A webhook tester fetches http://169.254.169.254/latest/meta-data/ and returns cloud credentials.

### Test for it

Submit URLs pointing to localhost, internal IPs and cloud metadata.

### How to fix it

Allow-list destinations, block internal IP ranges and disable redirects.

### Code samples

#### Vulnerable (python)

````python
url = request.json['url']
return requests.get(url).text
````

#### Secure (python)

````python
url = request.json['url']
if urlparse(url).hostname not in ALLOWED_HOSTS:
    return 400
return requests.get(url, timeout=5, allow_redirects=False).text
````

### Quiz

#### api-2023-q03 (medium)

An endpoint accepts a URL from the user and fetches it. How do you prevent SSRF?

1. Allow-list destinations and block internal IP ranges **(correct)**
2. Base64-encode the URL before fetching
3. Disable TLS verification

Explanation: The server must restrict where it can connect: allow-list known hosts, block loopback, private and metadata addresses, and disable redirects.

- [OWASP API Security Top 10 2023 — API7 Server Side Request Forgery](https://api-security.owasp.org/editions/2023/en/0xa7-server-side-request-forgery/)

## API8 — Security Misconfiguration

- Risk ID: `api-2023-API08`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Missing hardening, permissive CORS and verbose errors expose the API.

### Real-world example

The API answers Access-Control-Allow-Origin: * on authenticated endpoints.

### Test for it

Check CORS, headers, error messages and exposed admin routes.

### How to fix it

Harden baselines, restrict CORS, disable debug and unused features.

### Code samples

#### Vulnerable (javascript)

````javascript
app.use(cors({ origin: '*' }));
app.use(errorHandler({ stack: true }));
````

#### Secure (javascript)

````javascript
app.use(cors({ origin: ['https://app.example.com'], credentials: true }));
app.use(errorHandler({ stack: false }));
````

### References

## API9 — Improper Inventory Management

- Risk ID: `api-2023-API09`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Old, undocumented or test APIs stay exposed.

### Real-world example

A /v1/beta login endpoint still accepts credentials after v2 replaced it.

### Test for it

Look for /v1, /beta and /internal paths and forgotten hosts.

### How to fix it

Keep an API inventory, retire old versions and track data flows.

### Code samples

#### Vulnerable (nginx)

````nginx
location / { proxy_pass http://api_v1; }
location /beta { proxy_pass http://api_beta; }
````

#### Secure (nginx)

````nginx
location /v2/ { proxy_pass http://api_v2; }

# v1 and beta are retired and return 410.
location /v1/ { return 410; }
location /beta { return 410; }
````

### References

- [OWASP API Security Top 10 2023 — API9 Improper Inventory Management](https://api-security.owasp.org/editions/2023/en/0xa9-improper-inventory-management/)

## API10 — Unsafe Consumption of APIs

- Risk ID: `api-2023-API10`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Third-party API data is trusted without validation.

### Real-world example

The app stores whatever a partner API returns, including oversized fields that later break its own clients.

### Test for it

Feed malformed or oversized data through mocked upstreams.

### How to fix it

Validate third-party responses, use TLS and set timeouts.

### Code samples

#### Vulnerable (python)

````python
data = requests.get(partner_url).json()
db.save(data)
````

#### Secure (python)

````python
data = requests.get(partner_url, timeout=5).json()
payload = PartnerSchema.model_validate(data)
db.save(payload.model_dump())
````

### Quiz

#### api-2023-q05 (medium)

What is the right way to consume a third-party API response?

1. Trust it because the connection uses TLS
2. Validate it against a schema and set timeouts **(correct)**
3. Store it raw and parse it on every read

Explanation: TLS protects the transport but says nothing about the content. Validate the payload and bound the call with timeouts and size limits.

### References

- [OWASP API Security Top 10 2023 — API10 Unsafe Consumption of APIs](https://api-security.owasp.org/editions/2023/en/0xaa-unsafe-consumption-of-apis/)

- Set rate limits and payload limits
- Block requests to internal addresses (SSRF)
- Keep an inventory of all API versions
