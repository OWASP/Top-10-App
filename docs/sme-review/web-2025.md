## A01 — Broken Access Control

- Risk ID: `web-2025-A01`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Users act outside their intended permissions.

### Real-world example

Changing /invoice/1001 to /invoice/1002 shows another customer's invoice.

### Test for it

Swap object IDs between two accounts. Call admin endpoints as a normal user.

### How to fix it

Deny by default. Enforce ownership on the server. Log access failures.

### Code samples

#### Vulnerable (javascript)

````javascript
app.get('/invoice/:id', (req, res) => {
  res.json(db.invoice(req.params.id));
});
````

#### Secure (javascript)

````javascript
app.get('/invoice/:id', (req, res) => {
  const inv = db.invoice(req.params.id);
  if (!inv) return res.sendStatus(404);
  if (inv.ownerId !== req.user.id) return res.sendStatus(403);
  res.json(inv);
});
````

### Quiz

#### web-2025-q01 (easy)

A user changes an ID in the URL and sees someone else's data. Which category fits?

1. Injection
2. Broken Access Control **(correct)**
3. Cryptographic Failures

Explanation: The server failed to check that the caller owns the requested object. That is broken access control, specifically object-level authorization.

## A03 — Software Supply Chain Failures

- Risk ID: `web-2025-A03`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Compromised dependencies, build tools or updates enter the product.

### Real-world example

In 2018 the event-stream package was handed to a new maintainer, who shipped version 3.3.6 with a dependency that stole cryptocurrency wallet credentials.

### Test for it

Generate an SBOM, run SCA scans, and look for typosquatted names and unpinned ranges.

### How to fix it

Pin exact versions, commit lockfiles, verify signatures and provenance, restrict CI secrets, and review dependency changes.

### Code samples

#### Vulnerable (json)

````json
{
  "dependencies": {
    "some-package": "*"
  }
}
````

#### Secure (json)

````json
{
  "dependencies": {
    "some-package": "1.4.2"
  }
}
````

### Quiz

#### web-2025-q03 (medium)

Which practice best reduces software supply chain risk?

1. Using the latest version of every package
2. Pinning versions and verifying signatures **(correct)**
3. Disabling TLS to simplify builds

Explanation: Exact pins, committed lockfiles and signature or provenance checks make unexpected updates and tampering detectable.

### References

- [OWASP Top 10:2025 — A03 Software Supply Chain Failures](https://owasp.org/Top10/2025/A03_2025-Software_Supply_Chain_Failures/)

## A04 — Cryptographic Failures

- Risk ID: `web-2025-A04`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Sensitive data is protected weakly or not at all.

### Real-world example

Passwords stored as unsalted MD5 are cracked within minutes of a leak.

### Test for it

Look for plain HTTP, weak ciphers, hard-coded keys and fast hashes such as MD5 or SHA-1.

### How to fix it

Use TLS everywhere, modern algorithms such as Argon2id, managed keys, and never roll your own crypto.

### Code samples

#### Vulnerable (python)

````python
import hashlib
hash = hashlib.md5(password.encode()).hexdigest()
````

#### Secure (python)

````python
from argon2 import PasswordHasher

ph = PasswordHasher(time_cost=2, memory_cost=19456, parallelism=1)
hash = ph.hash(password)  # Argon2id with a per-password salt
````

### Quiz

#### web-2025-q05 (medium)

Which is the safe way to store user passwords?

1. MD5 without a salt
2. Encrypting with a shared key
3. Argon2id with a per-password salt **(correct)**

Explanation: Argon2id is a slow, memory-hard password hash with a unique salt, which resists cracking after a breach. Fast hashes and reversible encryption are not suitable.

- [OWASP Top 10:2025 — A04 Cryptographic Failures](https://owasp.org/Top10/2025/A04_2025-Cryptographic_Failures/)

## A05 — Injection

- Risk ID: `web-2025-A05`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Untrusted input is executed as a command or query.

### Real-world example

Entering ' OR 1=1-- in a login box bypasses authentication.

### Test for it

Send quotes, separators and template syntax. Watch for errors and timing changes.

### How to fix it

Use parameterized queries, validate input, and give the database account least privilege.

### Code samples

#### Vulnerable (python)

````python
cursor.execute("SELECT * FROM users WHERE name='" + name + "'")
````

#### Secure (python)

````python
cursor.execute("SELECT * FROM users WHERE name = %s", (name,))
````

### Quiz

#### web-2025-q02 (easy)

What is the best defense against SQL injection?

1. Parameterized queries **(correct)**
2. Hiding error messages
3. Longer passwords

Explanation: Parameterized queries keep data out of the SQL syntax, so input cannot change the structure of the query. Hiding errors only reduces leakage.

- [OWASP Top 10:2025 — A05 Injection](https://owasp.org/Top10/2025/A05_2025-Injection/)

## A06 — Insecure Design

- Risk ID: `web-2025-A06`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Security thinking is missing before the code is written.

### Real-world example

A password reset asks only for a birth date, which is easy to find online.

### Test for it

Run threat modeling on key flows and ask what an abuser would do.

### How to fix it

Threat model early, use secure patterns, and write abuse cases as tests.

### Code samples

#### Vulnerable (python)

````python
if dob == user.dob:
    allow_reset()
````

#### Secure (python)

````python
from itsdangerous import URLSafeTimedSerializer

serializer = URLSafeTimedSerializer(secret_key, salt='reset')
token = serializer.dumps(user.id)
user_id = serializer.loads(token, max_age=900)
# Also store a one-time nonce and reject a reused token.
````

- [OWASP Top 10:2025 — A06 Insecure Design](https://owasp.org/Top10/2025/A06_2025-Insecure_Design/)

## A07 — Authentication Failures

- Risk ID: `web-2025-A07`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Login, session or credential handling is weak.

### Real-world example

No rate limit lets an attacker try thousands of passwords per minute.

### Test for it

Try credential stuffing, weak passwords and session reuse after logout.

### How to fix it

Require MFA, rate limit attempts, use strong session management and breached-password checks.

### Code samples

#### Vulnerable (python)

````python
if pw == user.pw:
    login(user)
````

#### Secure (python)

````python
if not rate_limit(ip):
    return 429
if verify_password(pw, user.password_hash) and verify_mfa(user, code):
    login(user)
else:
    return 401
````

### References

- [OWASP Top 10:2025 — A07 Authentication Failures](https://owasp.org/Top10/2025/A07_2025-Authentication_Failures/)

## A08 — Software or Data Integrity Failures

- Risk ID: `web-2025-A08`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Code or data is trusted without verification.

### Real-world example

An app auto-updates from a server that does not sign its releases.

### Test for it

Check for unsigned updates, unsafe deserialization and unverified CI plugins.

### How to fix it

Sign and verify artifacts, avoid unsafe deserialization, and protect the build pipeline.

### Code samples

#### Vulnerable (shell)

````shell
curl -fsSL https://example.com/install.sh | sh
````

#### Secure (shell)

````shell
curl -fsSLO https://example.com/app.tar.gz
curl -fsSLO https://example.com/app.tar.gz.sig
cosign verify-blob --signature app.tar.gz.sig \
  --key pub.key app.tar.gz
````

## A09 — Security Logging & Alerting Failures

- Risk ID: `web-2025-A09`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Attacks go unnoticed or cannot be investigated.

### Real-world example

Thousands of failed logins are never noticed because nothing alerts.

### Test for it

Trigger failed logins and access errors. Check that they are logged, protected and alerted on.

### How to fix it

Log security events, protect log integrity, alert on abuse, and rehearse incident response.

### Code samples

#### Vulnerable (python)

````python
try:
    login(user)
except Exception:
    pass
````

#### Secure (python)

````python
try:
    login(user)
except Exception:
    logger.warning('login_failed user=%s ip=%s', user.id, ip)
    # Ship to the SIEM and alert when failures
    # exceed 50 per minute for one IP.
````

### References

## A10 — Mishandling of Exceptional Conditions

- Risk ID: `web-2025-A10`
- Status: **Awaiting SME review**
- Last reviewed: 2026-10-21

### Summary

Errors and edge cases cause unsafe behavior.

### Real-world example

A crash in the payment check makes the app approve the order anyway.

### Test for it

Send malformed input, timeouts and missing fields. Does the app fail closed?

### How to fix it

Fail closed, handle every error path, and hide internals from users.

### Code samples

#### Vulnerable (python)

````python
try:
    check_payment()
except Exception:
    approve()
````

#### Secure (python)

````python
try:
    check_payment()
except Exception as exc:
    deny()
    logger.error('payment check failed', exc_info=exc)
````

### Quiz

#### web-2025-q04 (easy)

When a security check throws an error, what should the app do?

1. Allow the action so the user is not blocked
2. Fail closed and log the error **(correct)**
3. Show the stack trace to the user

Explanation: Fail closed: deny the action, log the failure privately, and show a safe error. Allowing the action on an error path is how checks get bypassed.

### References

- [OWASP Top 10:2025 — A10 Mishandling of Exceptional Conditions](https://owasp.org/Top10/2025/A10_2025-Mishandling_of_Exceptional_Conditions/)
